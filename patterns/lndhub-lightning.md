# Pattern: LNDhub Self-Hosted Lightning Hub

LNDhub is an open-source accountancy layer that sits on top of a Lightning Network Daemon (LND) node, exposing per-user Lightning accounts over a REST API. BlueWallet developed LNDhub and uses it as the backend for its Lightning wallet type (`LightningCustodianWallet`).

## Core mechanism

1. **Shared node, individual accounts.** One LND node serves many users. Each user has a separate account (username/password pair) tracked in LNDhub's database; balances are accounting entries, not actual Lightning channels per user.

2. **Top-up via on-chain.** To fund a Lightning account, the user sends on-chain bitcoin to a dedicated top-up address generated by LNDhub. LNDhub credits their account balance.

3. **Outbound payments.** When a user pays a Lightning invoice, LNDhub pays the invoice from its shared channels and deducts the amount from the user's account balance.

4. **Inbound payments.** LNDhub creates a Lightning invoice on behalf of the user (using the hub's channels). When the invoice is paid, the hub credits the user's account.

5. **Credential format.** The wallet secret is stored as `<username>:<password>@<hub-url>`. This allows portability — any LNDhub-compatible wallet can connect to any LNDhub server.

## Trust model

LNDhub is **custodial by design** — the hub operator holds the bitcoin in their LND node's channels. The user trusts the operator to:
- Accurately record account balances
- Remain solvent and operational
- Not censor payments

This is fundamentally different from a self-custodial Lightning wallet (such as Phoenix or Breez), where the user holds their own channel keys.

**Self-custodial variant:** if a user self-hosts LNDhub pointed at their own LND node, the arrangement becomes self-custodial — no third-party trust required. This is the only self-custodial Lightning path in BlueWallet after the shutdown of `ln.bluewallet.io` on 31 May 2023.

## BlueWallet LNDhub discontinuation (31 May 2023)

BlueWallet operated a free, public LNDhub instance at `ln.bluewallet.io`. This was shut down on 31 May 2023 due to operational costs and sustainability concerns. After the shutdown:

- Existing users lost access to custodial Lightning unless they migrated to a third-party hub
- BlueWallet UI retained Lightning wallet creation but requires users to supply a custom LNDhub URL
- The `lightning-ark-wallet` (Arkade integration) was first introduced in v7.2.2 (24 November 2025) as an alternative path to off-chain payments; v8.0.0 (June 2026) upgraded the Ark SDK

## Self-hosting LNDhub

The LNDhub source code is at https://github.com/BlueWallet/LndHub (MIT licence). Typical self-hosting stack:
- Bitcoin full node (Bitcoin Core)
- LND (Lightning Network Daemon)
- LNDhub (Node.js service, connects to LND via gRPC)
- Redis (for session/account storage)

Platforms: Umbrel, Start9, RaspiBlitz, and Citadel all package LNDhub as installable apps, lowering the self-hosting barrier significantly.

## REST API endpoints (key)

| Endpoint | Purpose |
|----------|---------|
| `POST /create` | Create new account |
| `POST /auth` | Authenticate, receive access/refresh tokens |
| `GET /balance` | Get account balance |
| `GET /getbtc` | Get top-up address |
| `POST /payinvoice` | Pay a Lightning invoice |
| `POST /addinvoice` | Create a Lightning invoice |
| `GET /gettxs` | Get transaction history |

## Third-party LNDhub providers

After `ln.bluewallet.io` shutdown, users who don't self-host can use:
- **Alby** — hosted Lightning service with LNDhub-compatible API (https://getalby.com)
- **LNtxtbot** — Telegram-based Lightning bot with LNDhub endpoint
- **Various hosting providers** — many home-node platforms (Umbrel, Start9) auto-configure LNDhub on install

## Relationship to Ark (Arkade)

BlueWallet first introduced `lightning-ark-wallet` in v7.2.2 (24 November 2025), using the Ark protocol via Arkade SDKs (`@arkade-os/sdk`, `@arkade-os/boltz-swap`). v8.0.0 (June 2026) upgraded the existing Ark SDK integration. Ark is a second-layer protocol distinct from Lightning channels — it uses shared UTXOs (VTXOs) and a delegated signing model. The Arkade integration uses Boltz submarine swaps for on-chain ↔ off-chain conversion and a delegator service at `https://delegate.arkade.money`. This is trust-minimised (delegated signing rather than full custody) but not fully trustless.

## Contrast: Phoenix's self-custodial approach (ACINQ)

Phoenix wallet (iOS/Android, by ACINQ) represents the alternative paradigm: **fully self-custodial Lightning via single-channel splicing**. The contrast with LNDhub is instructive.

| Dimension | LNDhub (BlueWallet) | Phoenix (ACINQ) |
|-----------|---------------------|-----------------|
| Custody | Hub operator holds BTC in channels | User holds channel keys |
| Trust for funds | Full custodial trust | Trustless (user can force-close) |
| Channel management | Shared channels on hub LND node | One channel per user; auto-spliced |
| Routing | Hub routes via its channels | Trampoline via ACINQ node |
| Self-hosting | Yes (self-host LNDhub + LND) | No (ACINQ node only) |
| On-chain swaps | Submarine swap via Boltz or similar | Splice-in/splice-out (trustless) |
| Privacy | Hub operator sees all | ACINQ sees payment metadata |
| Scale | N users share M channels | 1 channel per user |

Phoenix cannot connect to an arbitrary node or be used with a self-hosted backend — ACINQ's node is the only permitted peer. This is the trade-off for automatic channel management without any custodial risk.

See [[patterns/self-custodial-lightning]] for a full description of Phoenix's architecture.
